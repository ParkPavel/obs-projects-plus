# План 3.7.3: проекты и шаблоны в хранилище

[English](plan-3.7.3.md) · [План развития](../ROADMAP-RU.md) · [Анонс следующих версий](next-versions-RU.md)

Статус: **проект спецификации для следующего цикла**, а не описание доступной функции. База исследования — выпущенная 3.7.2 и main a2f322d7 от 14.11.2026. Срок выпуска и окончательный файловый формат пока не назначены. Этот этап меняет только документы.

## Результат для пользователя

В видимой папке хранилища можно найти, прочитать и изменить описание своего проекта, сохранить его как шаблон и передать другому человеку обычной Markdown-заметкой. ИИ-инструмент с разрешённым доступом к хранилищу работает с тем же документированным интерфейсом; редактировать скрытый data.json для этого не требуется. Получатель видит состав шаблона, выбирает папки и применяет его без ручного восстановления связей.

Это особенно важно на iPhone/iPad, где работа со скрытой конфигурацией неудобна. Видимые файлы доступны через [Vault API](https://docs.obsidian.md/Plugins/Vault); скрытые папки требуют другого API. Переносим именно описания проектов, а записи пользователей остаются обычными заметками.

Эта инвентаризация — чтение указанных участков, не завершённый аудит всех мест записи. Первая задача реализации — найти все остальные вызовы и динамические конфигурации пользовательских видов.

## Предлагаемый файловый интерфейс

Папка по умолчанию **Projects Plus/**, с возможностью выбрать другое видимое место внутри хранилища. Это предложение для первого прототипа, а не уже поддерживаемый путь.

```text
Projects Plus/
  Projects/       активные описания проектов, по одной .md-заметке
  Templates/      переносимые шаблоны .md
  Recovery/       проверенные снимки и журналы восстановления
  README.md       инструкция для человека и ИИ-инструмента
```

Рекомендуемый прототип: обычный Markdown с пояснениями и одним помеченным JSON-блоком конфигурации. Небольшой frontmatter содержит тип документа, стабильный ID и версию оболочки; большой объект проекта не помещается в редактор стандартных свойств Obsidian. Маркеры, имена полей и JSON Schema утверждаются после испытания чтения/редактирования/Share на реальном iPhone. Альтернатива с полной конфигурацией в YAML сравнивается на тех же примерах; два равноправных формата одновременно не вводим.

Документ содержит только сериализуемые данные и декларативные правила. Текст заметки, импорт или инструкция ИИ не запускают JavaScript, команды ОС, скачивание вложений или сетевые действия.

| Объект | Где источник истины после включения файлового режима |
| --- | --- |
| Активное определение проекта | Его видимая заметка; память и индекс восстанавливаются из неё. |
| Шаблон | Отдельный неактивный документ. Само попадание файла в хранилище не создаёт рабочий проект. |
| Записи и значения полей | Исходные заметки пользователя; миграция конфигурации их не переписывает. |
| Устройство, UI-предпочтения и состояние синхронизации | Локальные настройки; не попадают в шаблон автоматически. |
| Восстановление | Отдельные снимки/журнал с понятным происхождением; не пересылаются вместе с шаблоном. |

Для ещё не переведённых проектов источником остаётся прежнее хранилище настроек. Переключение выполняется по явному состоянию миграции; два независимых источника истины и безусловная двойная запись запрещены. Кэш в data.json допустим только как перестраиваемый индекс, не единственная копия файлового проекта.

## Контракт без потерь

1. Сначала сохранить и перечитать исходные байты data.json, определения проектов и необходимые журналы. Ошибка копирования блокирует переход.
2. Декодировать в независимую модель проекта. Сохранить активные и архивные проекты, порядок, источники, поля, формулы и их семантику, связи, rollup, виды/блоки, Agenda, палитры, пути шаблонов, исключения и действующие счётчики ID. Провести отдельную инвентаризацию полей сторонних видов.
3. Создать документы в промежуточном состоянии, перечитать, проверить схему, ссылки и семантическое равенство исходной конфигурации. Не подменять неизвестные значения defaults.
4. Записать журнал перехода и переключить источник только после успешной сверки. Файловая синхронизация нескольких документов не является общей транзакцией: после обрыва загрузчик должен однозначно продолжить или восстановить старую согласованную версию.
5. Не удалять старую копию до подтверждённого перезапуска и проверки. Откат восстанавливает совместимый комплект версии плагина и настроек; правки после перехода предварительно сохраняются отдельно.

Неизвестная будущая версия или неподдерживаемая конфигурация открывается с объяснением и исходными данными, но не перезаписывается. Неизвестные поля нельзя молча выкинуть: сохранение исходного документа либо явный отказ безопаснее потери данных. Журнал различает запланировано, записано, перечитано, применено и восстановлено.

## Изменения через UI, заметку и ИИ

Все пути изменения проходят через общую валидацию и одну очередь для конкретного проекта. Внешнюю правку замечаем через события Vault и повторное чтение; операции массовой синхронизации объединяем без полного повторного сканирования хранилища на каждый символ.

Проверка актуальной ревизии/хеша выполняется внутри доступной read-modify-write операции; после записи нужен read-back. Это не распределённая блокировка других устройств или сторонних программ. При расхождении сохраняются обе версии и показывается конфликт — без автоматического last-write-wins. Некорректный JSON оставляет последнюю рабочую версию в памяти и исходный файл на диске; UI показывает, что новые изменения не применены.

Для ИИ публикуем схему, каталог разрешённых полей и минимальные примеры: создать проект, добавить вид/поле, связать проекты, изменить шаблон. Связь с конкретной моделью, встроенный чат, API-ключи и отдельный облачный сервис для этого не нужны. Правка определения не даёт права изменять все записи. Внешние управляющие заметки не должны попадать в обычные выборки данных самого плагина.

Переименование документа сохраняет ID; дубликат ID создаёт конфликт. Удаление файла не удаляет исходные заметки и не вызывает его тихое воссоздание. Семантику удаления/архивации и сохранения внешних правок проверяем отдельно. Recovery содержит личные настройки и участвует в политике доступа/синхронизации хранилища — это не публичная библиотека шаблонов.

## Шаблон и обмен одной заметкой

Шаблон включает схему полей, виды, фильтры, формулы, Agenda и необходимые текстовые шаблоны заметок. Он не включает реальные записи, архивные заметки, токены, историю UI, runtime-кэш или действующий счётчик записей. Внутренние пути, имена источников и выражения тоже могут раскрывать личную информацию: перед передачей нужен обзор содержимого и параметров.

Зависимые проекты оформляются как явный пакет в одной .md-заметке: один корневой проект и включённые определения зависимостей. При импорте создаём новые ID проектов/видов/блоков и перепривязываем типизированные ссылки. Не заменяем строковые подстроки по всему JSON, где могут находиться пользовательские тексты и формулы. Отсутствующая зависимость требует выбора существующего проекта либо отказа; повторный импорт не затирает уже работающий проект.

Пути папок и внешних источников получатель сопоставляет со своим хранилищем. Пустой путь не превращается автоматически в выборку всего хранилища. Перенос бинарных вложений и реальных записей не входит в базовый однофайловый шаблон; такие зависимости перечисляются явно. Текстовые шаблоны можно включать внутрь пакета с безопасными относительными именами. Запись вне выбранной папки, в .obsidian, через ../ или абсолютный путь запрещается.

Целевое действие — **«Поделиться шаблоном»**: подготовить переносимую заметку и вызвать штатный Share там, где существует поддерживаемая возможность. [Obsidian документирует Share для мобильных заметок](https://obsidian.md/help/more-options-menu). Наличие команды меню ещё не подтверждает публичный API вызова из плагина и сохранность машинного блока при отправке. Первый spike проверяет оба вопроса. До его результата нельзя обещать строго один тап: допустимый промежуточный путь — открыть готовую заметку и выбрать её нативное Share; на ПК — сохранить/открыть файл. Ни PDF, ни картинка, ни Obsidian URL не заменяют переносимый .md-пакет.

## Порядок реализации

| Этап | Результат и условие завершения |
| --- | --- |
| P0: инвентаризация и контракты | Найдены все поля/писатели/ссылки; составлена матрица сохранности, сравнение JSON/YAML и протокол Share. |
| P1: чистая модель и кодек | Schema, parse/validate/serialize и граф зависимостей работают независимо от UI; round-trip не теряет поддерживаемые настройки. |
| P2: файловый репозиторий | Чтение, запись, события, ревизии, конфликт, переименование и удаление; сбой не повреждает последнюю принятую версию. |
| P3: миграция и откат | Проверенные копии, журнал, прерывание в каждой точке, перезапуск и восстановление без переписывания исходных заметок. |
| P4: шаблоны и импорт | Просмотр состава, перепривязка зависимостей, безопасные пути, повторный импорт, отсутствие тихих сетевых/файловых действий. |
| P5: интеграция и приёмка | UI и ИИ-файл используют один контракт; обмен между двумя хранилищами, реальными ПК/iPhone и перезапуск проверены. |

## Приёмка 3.7.3

- Сохранить реальные сложные проекты из 3.7.2, перезапустить и сверить все поддерживаемые настройки, зависимости, показатели/результаты и счётчики; исходные записи побайтно неизменны.
- Применить шаблон практики с зависимостями к чистому хранилищу с другими путями и ID; данные не подмешиваются, связи ведут к нужным новым проектам/блокам.
- Изменить файл человеком и ИИ-инструментом, одновременно через UI и два устройства; конфликт не теряет ни одну версию. Проверить повреждение, дубликаты ID, новые версии схемы, rename/delete и отсутствие прав записи.
- Оборвать процесс во время каждого шага миграции/записи и воспроизвести восстановление. Отдельно проверить импорт более новой версии и неизвестных конфигураций.
- На реальном iPhone отправить и получить .md через выбранный штатный путь, убедиться в сохранности блока конфигурации и импортировать его. Передача между пользователями и синхронизация собственных устройств — разные проверки.
- Сравнить запуск и редактирование с 3.7.2 на одинаковом наборе данных: время, память, чтения/записи, события. Числовые бюджеты утверждаются по измеренной базе до рефакторинга; считать отсутствие регрессии установленным заранее нельзя.

## Границы и открытые решения

В 3.7.3 не включаем новый вычислительный движок, перенос сырых записей по умолчанию, маркетплейс, автоматическое исполнение текста ИИ или нативные виджеты ОС. Сохраняем существующее поведение формул и контролов 3.7.2.

До фиксации реализации решить: точные маркеры/схему документа, набор переносимых сторонних видов, границы пакета зависимостей, сценарий прямого Share и UX выбора конфликтующих версий. Для каждого решения нужен воспроизводимый пример и записанный результат, а не только макет интерфейса.
