# План 3.7.4: мобильные виджеты и напоминания

[English](plan-3.7.4.md) · [План развития](../ROADMAP-RU.md) · [Основа 3.7.3](plan-3.7.3-RU.md)

Статус: **направление исследований после 3.7.3**. Это целевой сценарий, не обещание готовой поддержки всех ОС и не описание функций 3.7.2. Даты не назначены. Изменения нативных приложений в этом этапе не выполняются.

## Цель

Сделать элементы Projects Plus доступными с мобильного устройства без постоянного поиска нужного экрана: обзор дня, следующая встреча, задачи, показатели и представления проекта. Добавить управляемые напоминания о событиях с понятным состоянием доставки на выбранных устройствах.

«Каждый элемент как виджет» означает полный каталог возможностей с явным статусом для каждой платформы: компактный вид, ограниченные действия, открытие полного экрана или недоступность с причиной. Это не обещание перенести весь интерактивный Svelte-интерфейс на домашний экран ОС.

## Два разных уровня

| Уровень | Что исследуем |
| --- | --- |
| Внутри Obsidian | Повторное использование блоков, календаря, Agenda, досок, галерей, таблиц и действий в компактных представлениях. |
| Системные виджеты iOS/Android | Нативное расширение/мост или приложение-компаньон, доступ к выбранным данным и переход к проекту. Обычного JS-плагина недостаточно, чтобы самостоятельно добавить расширение в чужое приложение. |

Apple описывает [WidgetKit как отдельную цель расширения приложения](https://developer.apple.com/documentation/widgetkit/creating-a-widget-extension), а Android — [свою систему app widgets](https://developer.android.com/develop/ui/views/appwidgets/overview). Поэтому до выбора решения нужен spike: существующие публичные возможности Obsidian, интеграция с нативным приложением, допустимый компаньон либо ограниченный альтернативный сценарий. Возможность редактировать исходники Obsidian, использовать приватные API или выпустить компаньон сейчас не предполагается.

## Контракты данных

Использовать стабильные определения проектов из 3.7.3 и отдельную ограниченную read-модель виджета: ID проекта/элемента, версия схемы, время обновления, небольшой набор данных, состояние устаревания и разрешённые действия. Виджет не становится вторым владельцем конфигурации проекта. Действия идут через проверяемую команду с актуальной ревизией; устаревшая карточка не перезаписывает новые данные.

Для каждого типа составить матрицу iOS/Android: доступные размеры, содержимое, частота обновления, действие по нажатию, приватность заблокированного экрана и поведение без открытого Obsidian. Первые кандидаты для прототипа — следующая встреча, Agenda на день, счётчик/показатель и быстрый переход. Остальные элементы остаются в каталоге; сокращение их возможностей должно быть явно показано.

Не предполагать, что компаньон автоматически получает доступ к sandbox Obsidian или iCloud-хранилищу. Проверить права, выбранный канал обмена, отсутствие сетевой передачи по умолчанию и работу без связи. Режим снимка должен показывать дату данных и не выдавать старую информацию за актуальную.

## Напоминания и доставка

1. Модель напоминания: стабильный ID события, момент/правило оповещения, часовой пояс, повторы, выбранные устройства, версия события и отмена. Отделить дату без времени от момента времени; определить DST и смену пояса.
2. Различать напоминание внутри открытого плагина, локально запланированное системное уведомление и удалённый push. Таймер JS и Notice в Obsidian не считаются доставкой после закрытия приложения.
3. Проверить доступный нативный адаптер и разрешения. [Apple описывает планирование через UserNotifications](https://developer.apple.com/documentation/usernotifications/scheduling-a-notification-locally-from-your-app); [Android13+ требует разрешение для обычных уведомлений](https://developer.android.com/develop/ui/compose/notifications/notification-permission). Эти API не становятся автоматически доступны плагину.
4. Сохранять состояния создано/запланировано/обновлено/отменено/отклонено/неизвестно. Подтверждение передачи ОС не означает, что человек увидел уведомление. Учитывать Focus, энергосбережение, запрет разрешений, фоновые ограничения и перезагрузку.
5. Обновление/удаление события отменяет старое расписание; повторная синхронизация идемпотентна. Политика «все выбранные устройства» или «одно основное» задаётся явно; глобальную доставку ровно один раз без координации не обещаем.

Если потребуется серверный push, отдельно решить согласие, стоимость, хранение адресов устройств и минимизацию данных. Настоящие токены остаются вне переносимых заметок и шаблонов. До платформенного прототипа публичная формулировка — «исследуем доставку на выбранных устройствах», а не «гарантируем сигнал на любом устройстве».

## Этапы и критерии перехода

| Этап | Проверяемый выход |
| --- | --- |
| W0: платформенная разведка | Матрица публичных API, ограничений, вариантов моста/компаньона; выбран осуществимый способ для каждой ОС либо записано отсутствие способа. |
| W1: общая проекция | Небольшой снимок элемента проекта, ревизия и переход к источнику без зависимости от UI-компонента. |
| W2: один системный виджет | Реальный iPhone/Android, закрытое приложение, устаревшие данные, lock screen и возврат к нужному проекту. |
| N0: модель событий | Часовые пояса, повторы, перенос/удаление, идентичность и конфликты расписаний проверены независимо от транспорта. |
| N1: один канал уведомлений | Разрешение/отказ, планирование/отмена, перезапуск и обновление события на реальном устройстве; ограничения записаны. |
| N2: несколько устройств | Выбор устройств, offline/resync, дубли, пропущенные события и смена основного устройства проверены. |
| W3: расширение каталога | Каждый элемент имеет явный уровень поддержки и сценарий приёмки; недоступность не маскируется пустым виджетом. |

Решение о составе 3.7.4 принимается после W0/N1 и оценки результатов 3.7.3. Если системная интеграция требует отдельного продукта или неподдерживаемого API, это отдельное решение, а не скрытая зависимость релиза.
