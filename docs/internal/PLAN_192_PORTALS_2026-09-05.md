## 0. Verdict first -- `document` vs `activeDocument` in `FloatingPopup`

**It is a defect, not a limitation.** Scope: any Projects leaf living in an Obsidian popout
window. Mechanism proven from code and typings; NOT observed in a running vault.

Evidence:

- `src/ui/components/FloatingPopup/FloatingPopup.svelte:258` -- `document.body.appendChild(node)`.
  The plugin bundle is evaluated in the main window's realm, so `document` is the main window's
  document, whatever window the node lives in.
- `node_modules/obsidian/obsidian.d.ts:259-264` -- Obsidian declares `activeWindow` /
  `activeDocument` precisely because "it will be different when using popout windows". A second
  document is a first-class state of the host, not a hypothetical.
- `esbuild.config.mjs:47-56` -- the `"document." -> "activeDocument."` replacement exists, but its
  `include` is `/svelte-dnd-action.*$/`. It rewrites the vendored drag library only. It does **not**
  rescue our own source. Any "the build fixes it" defence is refuted at that line.
- `CONTRIBUTING.md:85` -- "**No `document.*`** -- use `activeDocument` for multi-window support" is
  already this project's stated rule. `FloatingPopup.svelte:258` breaks a rule the repo wrote down.
- The same component binds its close paths to the main document:
  `FloatingPopup.svelte:89-92` (`document.addEventListener` for keydown and mousedown), and it
  measures against the main window at `:114-124` (`window.innerWidth/innerHeight`,
  `getComputedStyle(document.documentElement)`). So in a popout the popup is not only reparented
  into the other window -- its Escape and outside-click handlers listen in the wrong window, and its
  geometry is computed against the wrong viewport.
- It is reachable: `FloatingPopup` is consumed by `ui/components/Navigation/CompactNavBar.svelte`
  among a dozen others, and `CompactNavBar` is part of the plugin's own view shell -- it is the
  `.compact-navbar` inside `.projects-container` that
  `src/__tests__/A190_peekAnchoring.acceptance.test.ts:66-79` renders. Every view carries it.

**But `activeDocument` is not the fix either.** `obsidian.d.ts:255-264` defines it as the *actively
focused* document. The document that must receive the node is the one the node already lives in:
`node.ownerDocument`. Exactly one site in the tree gets this right today --
`src/ui/views/Calendar/components/Timeline/AgendaSidebar.svelte:496` (`const doc = node.ownerDocument`).
`activeDocument` remains correct for *creating* an element that has no parent yet
(`src/lib/dashboard-engine/accessibility.ts:227` shows the defensive `activeDocument ?? document`
idiom for that case).

Consequence for the ticket: #192 stops being pure maintenance debt. The consolidation carries one
behaviour fix, and that fix is the reason the primitive is worth building.

Not established here: what a user actually sees when it happens. Cross-document `appendChild`
adopts the node rather than throwing, so the likely symptom is "the popup vanishes from the popout
window and appears, mispositioned, in the main window". That sentence is a hypothesis until someone
pops out a Projects leaf and opens a popup. It belongs in the vault run, not in the gates.

## 1. Contract

One action moves a node out of its layout parent, and it guarantees:

1. **The node never leaves its own document.** The destination is derived from
   `node.ownerDocument` or from an ancestor of `node`; never from the module-scope `document`, and
   never from the focused document.
2. **The node never leaves its own leaf** unless the strategy says so. Two leaves put two
   `.projects-container` subtrees in one document -- the reason `overlayPortal.ts:12-19` derives its
   target by walking up instead of querying down.
3. **Destroy is idempotent and total.** Calling it twice is not an error; calling it when the
   target was never found is not an error.
4. **A missing target degrades, it does not throw.** The node stays where it is
   (`overlayPortal.ts:30-34` already states this and pays for it in geometry, knowingly).
5. **The target is resolved at mount, with at most one `tick()` retry**, and the retry is guarded
   by a `destroyed` flag so a late `appendChild` cannot resurrect an unmounted node
   (`overlayPortal.ts:21-28, 58-64`).

To whom: every component that today writes its own `portal*` function. Not to `FilterRow` -- see S4.

## 3. The primitive

New module `src/ui/portal.ts`. One exported Svelte action, **named `portal`** -- the name is
load-bearing, see Risks -- taking a target strategy:

- `"leaf-overlay"` -- today's `overlayPortal` behaviour, unchanged, including the retry, the
  `destroyed` guard and the stay-put fallback.
- `"document-body"` -- `node.ownerDocument.body`. This is the strategy that fixes S0.
- `"own-layer"` -- nearest `.workspace-leaf-content` / `.workspace-leaf`, with a container the
  action creates and owns; falls back to `node.ownerDocument.body`.

Shared, in the primitive rather than in six copies: idempotent destroy, the missing-target
fallback, the `tick()` retry with its `destroyed` flag, and the document resolution.

Deliberately NOT in the primitive: geometry. `AgendaSidebar`'s bounds tracking (`:502-522`) and
`DayPopup`'s pointer-events and layering are those components' own business; the primitive moves a
node and says where, nothing more.

`src/ui/app/overlayPortal.ts` keeps its path and its exported name `portalToOverlay`, re-expressed
as `portal` with `"leaf-overlay"`. That is a re-export, not a second implementation -- and it is
what keeps `A190` untouched through the whole sequence (Risks).

## 4. What stays outside the primitive, and why

- **`src/ui/views/Calendar/agenda/FilterRow.svelte`** -- three hand-built popovers appended to
  `activeDocument.body` at `:308`, `:367`, `:644`, built element by element from `:201` onward and
  torn down by `destroyFieldPopover`-style functions with an `(el as any).__vvCleanup` escape hatch
  (`:313-319`). These do not *move* a node the framework owns; they **construct** DOM imperatively
  and manage its whole life outside Svelte. A portal primitive has nothing to offer them. Their real
  fix is the migration this repo already performed elsewhere -- onto `FloatingPopup` / `PopoverList`
  -- which is a different change with a different acceptance surface (keyboard navigation, search,
  focus). **Separate ticket.** Folding it into #192 would make one change that both consolidates a
  primitive and rewrites three interactive surfaces, and only one of those two is reviewable.
- **`FloatingPopup`'s mobile branch** (`:270-286`) -- not portaled today, and a bottom sheet inside
  a backdrop has no reason to be. Leave it.
- **`DayPopup`'s promotion of the workspace leaf to `position: relative`** (`:124-127`) -- a host
  mutation with no undo. Out of the primitive; flagged in Risks.

## 5. Order -- each step lands with the four gates green

**Step 0 -- characterise before sharing.** New suite `src/__tests__/A192_portalContract.test.ts`
that pins today's behaviour of each of the six actions in jsdom: where the node lands, what a second
`destroy()` does, what happens with no target. No source change.
*Proof on landing:* the suite is green against unmodified code -- the only state in which it is
evidence that a later refactor preserved behaviour.
*It must also answer one open question* (S8): in Svelte 3.59.2, does the generated `d(detaching)`
detach the element before running the action's `destroy`? `node_modules/svelte/internal/index.mjs:418`
shows `detach` is null-safe, but the ORDER decides whether `AgendaSidebar.svelte:525-531`'s restore
branch is live code or dead code. Measure it; do not reason about it.

**Step 1 -- the primitive, with no caller changed.** Add `src/ui/portal.ts` and its unit tests;
rewrite `overlayPortal.ts` as a thin re-export.
*Proof:* new strategy tests green; `A190` green **unmodified** -- the assertion at
`A190_peekAnchoring.acceptance.test.ts:237-248` reads `SlideInPanel`'s text for two lines starting
`use:portalToOverlay` and for the import string `from "src/ui/app/overlayPortal"`, and both survive
by construction. Reversible: deleting the new file restores the old tree.

**Step 2 -- the two identical Calendar copies.** `HeaderStripsSection.svelte:29-36` and
`TimelineView.svelte:20-27` are the same function twice; both become
`use:portal={{ to: "document-body" }}`.
*Proof:* a test in `A192` that mounts the node inside a **second** `Document`
(`document.implementation.createHTMLDocument()` plus `adoptNode`) and asserts the node lands in
**that** document's body. That single test is the one that would have caught S0, and it is why this
step comes before the `FloatingPopup` step: it establishes the check on sites whose behaviour is
already right.

**Step 3 -- `FloatingPopup`.** Replace the local `portal` (`:257-264`) with the shared action.
This is the behaviour change of the ticket.
*Proof:* the second-document test above, now applied to `FloatingPopup`; plus
`FloatingPopup.test.ts` green **unmodified** -- in a single-document jsdom
`ownerDocument === document`, so `:102` and `:187` keep passing without an edit. If they need an
edit, the change was wider than planned: stop and re-plan.
*Not proven by any gate:* the popout window itself. That is a vault run with a Projects leaf moved
to its own window, and it belongs in the ticket's acceptance, not in the suite.

**Step 4 -- `AgendaSidebar`.** The move goes through the primitive; the bounds tracking stays.
The restore branch (`:525-531`) is decided by Step 0's measurement: dead, delete it and cite the
measurement in the commit; live, the primitive gains an explicit `restore` option, so that "what
destroy does" stays visible at the call site instead of hidden in one of six copies.

**Step 5 -- `DayPopup`.** `to: "own-layer"`. The container's class and its layering move with it.
The constraint that decides the implementation: the inline `cssText` at `:121` and `:134` is
invisible to R0.19, which scans style blocks and `.css` files only
(`src/__tests__/support/cssScan.ts:111-118`). Writing that layer into CSS as a raw number would
RAISE the raw layer count, and R0.19 is pinned exactly --
`R0_19_oneLayerScale.test.ts:128-133` asserts that one more raw value breaks it. So either keep the
layer inline, or put it on the `--ppp-z-*` scale. Never a raw number in CSS.

**Step 6 -- out of scope, filed not done.** `FilterRow` to `FloatingPopup`, as its own ticket (S4).

Reversibility: steps 1-2 revert cleanly with no data or contract implication. Step 3 changes
user-visible behaviour in one host configuration and is the step an adversarial review should be
pointed at. Steps 4-5 touch components with their own geometry and are the ones most likely to need
a screenshot rather than a gate.

Handoff budget: this plan, then implementer (steps 0-3), then auditor. Steps 4-6 are a second ticket
if the first three fill the budget.

## 6. Risks -- what breaks that the gates would not catch

1. **`A190`'s assertions are name-level, not behaviour-level.**
   `A190_peekAnchoring.acceptance.test.ts:243-247` counts lines beginning `use:portalToOverlay` and
   requires the literal import `from "src/ui/app/overlayPortal"`; `:250-259` requires the portal
   attribute to precede `use:focusTrap`. Keeping the module path and the export name means **zero
   changes to A190** in this ticket. If a later ticket collapses the re-export, those three
   assertions must be **rewritten against the new name, not deleted** -- the contract they encode
   (both root nodes ask to move; the move is declared before the trap) is unchanged, and a rewrite
   that drops either clause is a weakening and must be refused.
2. **R0.16's exemption for `FloatingPopup` is proven by a regex.**
   `R0_16_remInContainer.test.ts:98-100` exempts `FloatingPopup` as window-anchored, and `:404-410`
   accepts that exemption only if the file exhibits the mechanism: `position: fixed` in its styles,
   OR the token `use:portal` matched with a word boundary on both sides in live text.
   `use:portalToBody` and `use:portalTo` do NOT match that boundary. `FloatingPopup` would still
   pass through the `position: fixed` clause (`FloatingPopup.svelte:305`), but naming the shared
   action `portal` keeps **both** proofs alive. That is the concrete reason for the name in S3.
3. **R0.19 is a pinned equality, not a ceiling.** `R0_19_oneLayerScale.test.ts:116-133` -- the total
   may not exceed the budget AND one more raw value must break it, so the constant equals the tree.
   Any raw layer value this work removes from a style block requires **re-measuring** the constant,
   in the same commit, the way that file's own bumps log describes. Never decrement by arithmetic.
4. **R0.3 counts `.svelte` and `.css` only** (`R0_3_pxBudget.test.ts:32`). Moving code out of a
   component into `src/ui/portal.ts` can only lower the count, and that budget is a ceiling, so it
   is free -- but the new module must ship no absolute units in any CSS, and the constant must not
   be raised for any reason.
5. **R0.6 has no ceiling for any file this touches.** `R0_6_locBudget.test.ts:14-65` lists
   `ui/views/Dashboard/**` only. There is nothing to lower and nothing to cut -- and, importantly,
   nothing stops these components growing. Do not "make room" anywhere; there is none to make. A new
   file outside `ui/views/Dashboard/**` needs no budget entry, which also means the primitive has no
   ceiling. Keep it small on merit.
6. **Cross-document Svelte scoped styles.** A portaled node keeps its `svelte-*` class, but the
   scoped rules live in the document where the component's styles were injected;
   `AgendaSidebar.svelte:1446-1447` already documents having to use `:global` for exactly this
   reason inside one document. Moving a node to a *different* document is a stronger version of the
   same hazard, and no jsdom test can see it.
7. **`DayPopup` mutates the host leaf** (`:124-127`, static to relative) and never undoes it.
   Consolidation must not silently drop that mutation -- the popup would then be positioned against
   the wrong box -- nor silently generalise it to every strategy.
8. **The gates cannot see any of this in a popout window.** Four green gates plus a green `A192`
   prove the mechanism, not the screen. The acceptance for step 3 is a vault run with a Projects
   leaf in its own window; if that run does not happen, the ticket reports the fix as *mechanism
   proven, screen unverified* -- in those words.

## 7. Rejected

- **"Portal everything to the body."** Rejected: it deletes #190's guarantee that a peek panel lands
  in **its own leaf's** layer, which `A190_peekAnchoring.acceptance.test.ts:331-354` pins for the
  split-pane case, and it would move `DayPopup` out of the sidebar boundary it deliberately respects
  (`DayPopup.svelte:107-114`).
- **"Let the caller pass the target element."** Rejected for the reason already written at
  `overlayPortal.ts:12-19`: a caller that cannot name the layer cannot name the wrong one. A
  parameterised target reintroduces the split-pane bug the derivation exists to prevent.
- **"Use `activeDocument` everywhere."** Rejected: `obsidian.d.ts:255-264` defines it as the
  *focused* document, so a component mounting while another window has focus would portal into the
  wrong window -- the same class of bug as S0 with a different trigger. The node's own document is
  the answer, as `AgendaSidebar.svelte:496` already has it. `activeDocument` stays correct only for
  creating a parentless element.
- **"Fix `FloatingPopup` with a one-word edit and close the ticket."** Rejected: the word is the
  smaller half. The same component binds Escape and outside-click to the main document
  (`FloatingPopup.svelte:89-92`) and measures against the main window (`:114-124`). A one-word fix
  would move the node correctly into a window where it still cannot be closed by clicking away.
  Either the whole component becomes document-aware, or the ticket states plainly that only the
  reparenting is fixed. This plan takes the second and says so here.
- **"Include `FilterRow` in the consolidation."** Rejected, with the reason in S4.
