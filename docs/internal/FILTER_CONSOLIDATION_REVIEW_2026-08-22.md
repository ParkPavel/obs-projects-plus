## 1. Ментальная модель эссе (8 сцен → принципы)

| Сцена | Принцип UX (что пользователь ХОЧЕТ ощущать) |
|---|---|
| 1. Дашборд | рабочая поверхность; правка в одном виде мгновенно видна во всех |
| 2. База из заметок | папка УЖЕ база; новое поле честно пишет frontmatter |
| 3. Двунаправленность | прозрачный контракт UI↔frontmatter, видно «что где меняется» |
| 4. Связи = нервная система | relation → related records → rollup → cross-base analytics |
| 5. **Фильтры = кросс-базы** | сохранённый именованный фильтр САМ становится базой со своими видами |
| 6. Аналитика-подсказка | проактивные агрегаты по типам; формулы спрятаны за UI («жесты и слова, не код») |
| 7. Интуитивность | никаких модалок с 40 настройками; drag&drop; прогрессивное раскрытие; шаблоны; объяснения на месте |
| 8. Дашборд = markdown-файл | конфиг читаем/версионируем |

**Ключ для нашей темы:** сцены 5, 6, 7 прямо отрицают «конвейер» как первичный способ. Пользователь
хочет «посчитать сумму по клиенту» через подсказку/свойство, а не собирать шаг pivot в редакторе.

## 2. Notion-эталон (из `NOTION_DM_RESEARCH.md` — уже утверждён репозиторием 2026-06-12)

**«В Notion НЕТ пользовательского конвейера трансформаций.»** Каждая операция живёт у своего объекта,
мгновенно, без Save:

| Операция | Дом в Notion | Наш эквивалент (по NOTION_DM_RESEARCH §2) |
|---|---|---|
| Фильтр | pills вида / View options ▸ Filter | filter-pills в ControlBar вида (уже FilterPanel) |
| Сортировка | View options ▸ Sort | меню/тулбар вида |
| Группировка | View options ▸ Group | ✅ сделано (W1: меню колонки) |
| **Агрегация** | футер колонки «Calculate» | Calculate у колонки/футере — **НЕ шаг конвейера** |
| **Вычисление** | Formula-**свойство** | FormulaConstructor #077 — **свойство, не шаг** |
| **Cross-DB** | Relation + Rollup **свойства** | свойство блока/поля — не пайплайн |
| **Join** | (нет; relation) | свойство БЛОКА «Дополнительный источник» |
| **Unnest** | нет аналога (массивы = multi-select/relation) | свойство БЛОКА «Развернуть список: <поле>» (toggle) |
| **Pivot/unpivot** | нет | **ЕДИНСТВЕННОЕ**, что остаётся в «Расширенных преобразованиях» |

**4 принципа Notion:** (1) нет режима редактирования данных-вида → **нет Save/Cancel**, страховка =
Undo + видимые pills; (2) операция у объекта, не в общем «процессоре»; (3) каждое правило видно и
снимается одним кликом; (4) live-результат всегда на экране.

## 3. Критика `FILTER_CONSOLIDATION_DESIGN.md`

### ✅ Что дизайн сделал ПРАВИЛЬНО (Notion-совместимо)
- Свёл 6 слоёв фильтра к одному видимому фильтру (pills) на одном движке — это Notion «один фильтр, видимый».
- Убил обход canonical в filter-tabs (#117) — Notion: один компаратор, консистентная семантика Relation/Select.
- Зафиксировал один порядок + ADR (#116). Хорошо как инженерный инвариант.

### ⚠️ Где дизайн ПОД-заземлён (не сверялся с NOTION_DM_RESEARCH)
Дизайн опирался на аудит кода + PRODUCT_RESET §R2, но **не открывал `NOTION_DM_RESEARCH.md`** —
поэтому переизобрёл более слабую модель, чем уже утверждённая:

1. **Ось «C Advanced» слишком толстая.** Дизайн оставляет в конвейере `pivot/join/unnest/unpivot/`
   `aggregate/compute/group-by(частично)`. Notion-эталон говорит: `aggregate → Calculate у колонки`,
   `group-by → вид` (✅ W1), `compute → formula-свойство` (#077 ✅), `join → свойство блока`,
   `unnest → свойство блока (toggle)`. **В конвейере остаются ТОЛЬКО `pivot/unpivot`.** Дизайн «прячет
   конвейер за Advanced» — эталон **растворяет** его почти целиком.

2. **Не адресована ГЛАВНАЯ боль — Save-режим.** «Непонятно как работает конвейер» — это в т.ч. то, что
   draft применяется только по «Сохранить», а за попапом живёт старая версия (NOTION_DM_RESEARCH §3:
   🔴 «ядро жалобы»). Эталон требует: advanced-редактор **без Save**, каждый шаг живьём показывает N→M,
   шаг-с-0 подсвечен «Отключить шаг». Дизайн трактует конвейер как `widget.transform за Advanced`, но
   **не убирает Save и не делает его живым** — а это и есть суть претензии пользователя.

3. **«3 оси A/C/B» — это модель ДВИЖКА, а не пользователя.** Порядок применения A→C→B хорош как
   внутренний инвариант. Но пользовательская модель (Notion/эссе) — **«операция живёт у своего объекта»**:
   фильтр — у вида, расчёт — у колонки, связь/rollup — у свойства. Юзер не должен думать «осями» —
   он должен находить операцию там, где привык. Оси оставить как engine-invariant (#116), но
   пользовательский deliverable формулировать как «каждая операция у своего дома», не «3 оси».

4. **Сцена 5 (фильтры-как-кросс-базы) не покрыта.** Сохранённый именованный фильтр, становящийся базой
   со своими видами — отдельная Notion-plus фича, её нет ни в дизайне, ни в roadmap. Зафиксировать.
