# План #184 — «Сохранить этот фильтр как источник»

**Ветка:** `feat/184-saved-filter` | **База:** `main = c079801` | **Проход:** архитектурный, read-only.

> Записано `lead`-ом с финального сообщения архитектора (у роли нет `Write`). Раздел
> «Проверка утверждений плана» в конце — мой, дописан после сверки с деревом: часть чисел плана
> измерена заново, и одно из них разошлось.

## Contract

1. **Блок может смотреть на ОДИН источник проекта** вместо слияния всех. `sourceId` отсутствует →
   кадр байт в байт тот же, что сегодня, и это проверяется тестом, а не рассуждением.
2. **Именованный источник, который сломан или ещё не приехал, выглядит не как пустая таблица.**
   Четыре состояния `resolveDerived` доходят до экрана, а не умирают в чистой функции.
3. **Фильтр, который пользователь уже видел работающим, получает имя** и становится
   `DerivedDataSource` в `additionalSources` проекта.
4. **Канонический порядок не меняется.** Разрешение источника — часть оси A, между `enrich` и
   `applyWidgetScope`.
5. Ни один существующий ключ не меняет смысла и ничего не мигрирует.

## Решение 1 — где разрешается derived-источник (главный вопрос)

### Ответ: в `WidgetHost`, между `enrich` и осью A. Порядок не меняется.

- `resolveDerived` при `from !== "project"` **не фильтрует part-кадр** — он берёт `ids` из part и
  отбирает строки обогащённого кадра. Значит `input.enriched` обязан быть целым обогащённым кадром,
  а `parts` — сырыми. Это ровно то, что есть в хосте: `frame` + `$frameParts`.
- Обогащение перенести нельзя: `relationFieldNames` берутся из `fields`, которые виджет получает от
  канваса, а не от провайдера. Мемоизация — отдельный тикет производительности.
- **«Per-widget обогащение» и «per-project frameParts» не конфликтуют**: они встречаются в хосте.
  `frameParts` — store, хост читает `$frameParts`; новых пропов через `DashboardCanvas → WidgetGrid`
  не нужно. Ради этого #170 и сделал его store, а не пропом.

```
$: projectEnriched = relationFieldNames.length > 0 ? enrichWithBacklinks(frame, relationFieldNames) : frame;
$: namedSource   = resolveNamedSource({ enriched: projectEnriched, parts: $frameParts, sources, sourceId });
$: enrichedFrame = namedSource.frame ?? projectEnriched;
$: scope         = applyWidgetScope(enrichedFrame, widget.config);   // литерал не тронут
```

**`enrichedFrame` остаётся именем кадра, уходящего в `applyWidgetScope`** — `R_filterOrder`
ищет подстроку `applyWidgetScope(enrichedFrame`. Переименование сломало бы инвариант 3 на ровном месте.

### Против канонического порядка

```
enrich → A0 (выбор источника + where выборки) → A1 (view.filter / filter-tab / subFilter) → C → B → sort → render
```

Это **не новая ось**, а второй участник существующей: ось A уже распределена по трём поверхностям,
добавляется четвёртая, самая верхняя внутри хоста. В `FILTER_ORDER_ADR.md` дописать сохранённый
источник **после** пиннутой подстроки `` `view.filter`, filter-tabs, `block.subFilter`, per-tab filter ``,
не внутрь неё.

### Мелочь, которую легко потерять

`frame`, приходящий в хост, — это `displayFrame` из `DashboardCanvas`, то есть уже суженный
`applyFilterTab`. Значит `enriched` — «проект как его видит текущий вид», а `parts` — сырые.
Пересечение по id даёт «строки этого источника, пережившие фильтр вида». Это правильно (обе — ось A)
и работает, потому что `resolveDerived` пересекает, а не объединяет. Назвать в комментарии, иначе
следующий читатель решит, что `enriched` — весь проект.

### Почему не `selectSourceFrame` «в лоб»

Она возвращает **сырой** part-кадр: без обогащения, без derived-колонок, без полей
`buildDisplayFrame`. Блок, указавший на обычную папку, потерял бы rollup-колонки. Поэтому из неё
берутся **id**, а строки — из обогащённого кадра, той же техникой, что внутри `resolveDerived`:

```ts
const part = selectSourceFrame(enriched, parts, sourceId); // не найден → enriched → пересечение = всё
const ids = new Set(part.records.map((r) => r.id));
return { fields: enriched.fields, records: enriched.records.filter((r) => ids.has(r.id)) };
```

### Ловушка, которую обязан обойти новый модуль

`sourceExists` проверяет **только `parts`**, а derived в `parts` не попадает никогда
(`isAcquirable` его исключает). Значит для derived-id `sourceExists` вернёт `false`. **Порядок
проверок обязан быть: сначала derived, потом `sourceExists`.** Наоборот — и каждая сохранённая
выборка вечно «сломана».

## Решение 2 — где живёт `sourceId` у блока без `sourceConfig`

### Ответ: там, где его объявил #170 — на `sourceConfig`, с `projectId: ""`.

- Пустой `projectId` уже означает «наследовать от вида»: `resolveBlockSource` на falsy `projectId`
  возвращает `{ kind: "parent" }`. То есть `{ projectId: "", sourceId }` — уже легальная и уже
  корректно обрабатываемая форма, а не новый ключ. Миграции нет.
- **Ключевой ход:** хост читает `widget.sourceConfig?.sourceId` напрямую, а не через `dbCall`.
  `resolveDbCallView` гейтит `sourceConfig` по типу `database-call`, но это неважно: выбор источника
  происходит **выше по течению**, чем `dbCall` (тот потребляет `transformedFrame`). Правка
  `linkedSourceState.ts` не нужна, и `data-table` работает наравне.
- **«`handleSourceChange` затирает `sourceId`» — верно наполовину.** Сброс при смене `projectId`
  **корректен**: `sourceId` называет источник *этого* проекта. Дефект в том, что нет второго
  селекта, который бы его ставил.
- Селект «источник внутри проекта» виден **только при `projectId === ""`** — иначе это видимое
  обещание без эффекта. Новый проп `projectSources` собирается из `project` через `sourceLabel`.
  Это **не** `availableSources` (там соседние проекты): два измерения, два селекта.
- Источники без `id` (созданные до #170) в список не попадают — на них нельзя сослаться. Нужна
  подсказка под селектом, иначе пользователь не поймёт, почему его вторая папка не предлагается.

## Решение 3 — как `broken` / `pending` попадают на экран

### Компонент `DatabaseCallBlock.svelte`, новый проп, а НЕ расширение `BlockSource`.

Он — единственный контентный компонент и для `data-table`, и для `database-call`, и у него уже есть
цепочка состояний источника на `EmptyState`. Готовый дом.

**Почему не расширять `BlockSource`:** `isExternalSource` определён как `kind !== "parent"`, а
`renderContext.ts` на `isExternal` обнуляет `pipelineStepCount`, `pipelineInputRowCount` и
`dbCallScopeApplied`. Сломанный именованный источник начал бы врать про пайплайн — тихая регрессия.

```ts
export type NamedSourceView =
  | { kind: "ok"; frame: DataFrame; sourceId: string | undefined }
  | { kind: "empty"; frame: DataFrame; label: string }
  | { kind: "broken"; reason: string; label: string }
  | { kind: "pending" };
```

| Состояние | Что на экране | Почему |
|---|---|---|
| `pending` | `EmptyState icon="loader"`, «Готовим сохранённую выборку…» | Обогащённый кадр ещё не приехал. Копия **отличается** от «Loading the linked project…»: причина другая. |
| `broken` | `EmptyState icon="unlink"`, «Источник, на который смотрит блок, исчез», `hint={reason}` | Конфигурация, которую можно починить; «0 записей» отправит смотреть на данные — не туда. |
| `empty` | Существующий пустой стейт + `hint` с `sourceLabel` | Настоящий ответ, а не сбой. Отдельная поверхность его переоценит. |
| `ok` | Ничего нового | Кадр уходит дальше. |

**Порядок ветвей:** после трёх `sourceState`-ветвей и перед `{:else if tabs.length === 0}`. Внешний
проект выигрывает — при внешнем `projectId` `sourceId` игнорируется по конструкции.

## Решение 4 — дом шага 2

### `ViewFilterBar.svelte` (`src/ui/components/FilterPills/`), потолка R0.6 нет.

- `filter`, `fields`, `records` уже есть; **`project` — нет**, добавляется один проп (в `App.svelte`
  он в области видимости).
- Запись: `settings.updateProject({ ...project, additionalSources: [...(project.additionalSources ?? []), derived] })`
  — тот же путь, которым пишет `CreateProject`. `id: uuidv4()`, `from: "project"`.
- **Ловушка тикета реальна, но проявляется иначе, чем он думал.** `ViewFilterBar` получает кадр
  **до** обогащения, поэтому `FilterPanel` предлагает поля сырого кадра — rollup там не будет.
  Выборка, построенная здесь, всегда выразима и всегда сработает при разрешении в хосте. То есть это
  не «сохранили слишком рано», а **более узкий выбор полей, чем позволяет модель**. Ограничение
  шага 2, записать в `VISION_DEVIATIONS.md` тем же коммитом.
- **Диалог имени — не модалка:** `ViewFilterBar` уже монтирует `FloatingPopup`; имя вводится инлайн
  в подвале того же поповера.
- Действие показывается только при `conditions.length > 0 && !readonly`: выборка, равная своему
  основанию, бесполезна.

## Решение 5 — отгружается ли шаг 1 в одиночку

**Да.** `CreateProject` уже создаёт `additionalSources` с `id` и `name`, identity переживает смену
kind. То есть сегодня, до всякого derived, у пользователя может быть проект с тремя именованными
источниками, и он не может показать их по отдельности. Шаг 1 даёт «проект = клиенты + архив, а этот
блок показывает только клиентов» — сцена 5 в слабой форме, полезная сама по себе. Обратный порядок
запрещён: шаг 2 без шага 1 даёт объект, которого нигде не видно.

## Risks — чего ворота не поймают

1. **`frameParts` пуст, когда блок его читает.** Провайдер пишет его внутри `querying`-промиса, слот
   рендерится в `{:then}`. Но это глобальные store: при **смене проекта** мгновение живут части
   предыдущего. Блок с `sourceId` покажет `broken`, мигнёт и починится. Смягчение: `pending` перед
   `broken` в порядке ветвей + живой прогон со сменой проекта.
2. **Два проекта в одном воркспейсе делят `frameParts`.** Store один. Спасает то, что внешний
   `projectId` игнорирует `sourceId`. Комментарий на месте гейта обязателен.
3. **`id` источника не гарантирован** — созданное до #170 живёт без него, селект такие не покажет
   молча. Отсюда обязательная подсказка.
4. **`resolveDerived` пересекает по `record.id`.** Если `mergeDataFrames` дедуплицирует записи с
   одинаковым id из двух источников, «источник A» покажет запись из B. `mergeFrames.ts` архитектором
   **не прочитан** — проверить в реализации одним тестом на пересекающиеся папки.
5. **`buildDisplayFrame` мог добавить поля, которых нет в part** — колонки сохранятся, но подпись
   «этот источник» будет над колонками, которых у источника нет. Косметика, назвать в PR.
6. **Правка `R_filterOrder` — самая заметная точка атаки.** Ответ обязан быть в коммите:
   композиционный тест **строже** подстрочного.

## Rejected

1. Разрешать derived в слое datasource — опровергнуто на Gate 0 в #170, запиннуто тестом.
2. Перенести обогащение в провайдер — `relationFieldNames` приходят от канваса, а не от провайдера;
   перенос сделал бы виджетное обогащение проектным.
3. `selectSourceFrame` для рендера напрямую — вернёт сырой part, потеряются derived-колонки.
4. Расширить `BlockSource` вариантами `broken`/`pending` — `isExternalSource` = `kind !== "parent"`,
   и сломанный источник начал бы врать про пайплайн.
5. Новый ключ `widget.sourceId` рядом с `sourceConfig` — раскол ровно того сорта, что стоил проекту
   `DataTableConfig.subBases`.
6. «Сохранить как источник» в `CreateProject` — там нет ни кадра, ни записей.
7. Модалка для имени — `FloatingPopup` уже смонтирован.
8. Объединить выбор проекта и выбор источника в один селект — это два измерения.
