# Product Reset — исходный мандат и стек разработки

> **Дата:** 2026-07-18  
> **Статус:** active product contract for all new product work  
> **Источник истины:** `DASHBOARD_V2_VISION.md` и исходное пользовательское эссе.  
> **Не отменяет:** технические инварианты `AGENTS.md`, текущие bugfix-стеки и уже закрытые тикеты.

## 1. Решение

Проект не оценивается по числу виджетов, формул или панелей. Он оценивается по тому,
может ли не-программист превратить свои Markdown-записи в понятную, локальную и живую
систему данных. Новая функциональность обязана приближать один из пользовательских
сценариев ниже. Если она не делает этого, она относится к обслуживанию/исправлениям,
а не к развитию продукта.

**Текущий незакоммиченный стек #105–#109 не откатывается.** Он стабилизирует существующий
опыт, но не является доказательством product readiness и не меняет приоритетов ниже.

## 2. Неподвижные продуктовые принципы

1. **Markdown-first.** Папка, теги и заметки уже являются данными; плагин не требует предварительно перенести их в закрытую схему.
2. **Одна сущность в двух интерфейсах.** Редактирование в представлении пишет в исходный Markdown, внешняя правка Markdown отражается в каждом связанном представлении.
3. **Relation-first.** WikiLink является внешним ключом. Relation, обратная связь, связанные записи, rollup, фильтрация и аналитика используют одну и ту же модель.
4. **Фильтр — живая база.** Сохранённая выборка имеет имя, представления и реактивно меняет состав по данным.
5. **Подсказать до настройки.** Система предлагает полезные действия по типам и связям данных; сложные формулы и transforms остаются advanced mode.
6. **Прогрессивное раскрытие.** Первый путь — шаблон или три простых действия; терминология и технические параметры появляются только при реальной необходимости.
7. **Прозрачность и переносимость.** Пользователь понимает соответствие UI ↔ frontmatter и может прочитать, скопировать и версионировать конфигурацию дашборда.

## 3. Главный диагноз: три несовместимые «связи»

Сейчас один пользовательский термин покрывает три отдельных механизма:

| Механизм | Реальность | Пользовательский разрыв |
|---|---|---|
| Relation-поле | WikiLink во frontmatter; picker есть в Table Grid | Нет единого флоу «поле A связано с базой/полем B», preview совпадений и обратной связи |
| `linkedSelection` | Выбор записи в одном dashboard-block фильтрует другой блок | Это реактивный фильтр блоков, а не создание relation-свойства |
| cross-source correlation | Join полей для отдельных chart-сценариев | Это аналитический join, не relation и не должно маскироваться под него |

### Каноническое решение

Relation — первичная доменная сущность. `linkedSelection` и correlation обязаны использовать/объяснять Relation, когда он существует, но не создают параллельной семантики связи. Пользовательский flow должен быть таким:

1. Выбрать поле или карточку → **«Связать с базой»**.
2. Выбрать целевую базу и поле-идентификатор; увидеть preview совпадений и unmatched records.
3. При необходимости создать обратное поле.
4. Сразу увидеть доступные действия: «Связанные записи», «Добавить rollup», «Построить динамику», «Создать связанный блок».
5. Перетаскивание карточки на карточку — быстрый путь создания значения Relation; контекстное меню остаётся доступной альтернативой.

## 4. Матрица сцен исходного запроса

| Сцена | Обязательный результат | Статус на 2026-07-18 | Критерий готовности |
|---|---|---|---|
| 1. Рабочая поверхность | Дашборд как главный экран с связанными представлениями | Частично | Изменение в одном view видно во всех релевантных view без ручного refresh |
| 2. База из заметок | Папка становится базой; новое поле честно записывается в frontmatter | Частично | Create field показывает последствия bulk-write и создаёт поле без потери данных |
| 3. Прозрачная двунаправленность | Пользователь видит, что и где меняется в файле | Gap | Hover/inspect показывает frontmatter key; открытие записи ведёт к источнику |
| 4. Связи как нервная система | Relation → related records → rollup → cross-base analysis | P0 gap | Demo «Клиенты → Сеансы» проходится без документации и ручной настройки фильтров |
| 5. Фильтры как базы | Сохранённая именованная выборка живёт и обновляется | Частично | Пользователь создаёт named saved filter и открывает его как источник view |
| 6. Аналитика-подсказка | Система предлагает Stats/chart/relation actions по данным | Gap | Новое Number/Date/Relation поле вызывает объяснимую, dismissible suggestion |
| 7. Интуитивный первый опыт | Шаблоны, progressive disclosure, примеры в UI | Gap | Новый пользователь достигает первого результата через профиль за ≤5 минут |
| 8. Дашборд как файл | Конфиг читаем, переносим и versionable | Decision gap | Принято и реализуется решение: Markdown/YAML-конфиг или документированный defer |

## 5. Новый порядок разработки

### R0 — Product-contract baseline

- Зафиксировать эту матрицу в backlog и в Definition of Done будущих работ.
- Провести ручной audit эталонного сценария «Клиенты → Сеансы» в чистом vault: screenshots, фактические шаги, ошибки и время до первого результата.
- Не объявлять Dashboard V2 «Notion-grade» или product-ready только по техническим 4 gates.

### R1 — Relation-first vertical slice (P0)

- Одна модель Relation во всех entry points: schema editor, cell/record editing, dashboard.
- Guided setup: target base, mapping/preview, inverse relation, invalid/unmatched state.
- Related-records surface и минимум один rollup (`count`) без ручного pipeline.
- Связанный `database-call` создаётся из Relation, а `linkedSelection` объясняет, какую relation он применяет.
- End-to-end demo acceptance: Client → Session → client card sessions count → date/pain chart.

### R2 — Понятные представления вместо параметров движка (P0/P1)

- Filter, sort, group и property configuration живут в view-level UI с человеческими описаниями и preview результата.
- Transform pipeline остаётся для pivot/join/advanced transformations и явно маркируется как advanced mode; не является первым способом выполнить обычную задачу.
- Любой select/config control объясняет результат и имеет пример, а не только имя поля.

### R3 — Доверие, discovery и первый опыт (P1)

- Field transparency: UI → frontmatter mapping, inspect/open source.
- Smart suggestions по Number, Date и Relation с безопасным dismiss.
- Профили «Клиенты», «Тренировки», «Дневник проекта»; zero state с тремя простыми действиями.
- Drag-to-link и drag-to-add-field планируются как direct-manipulation слой поверх стабильной Relation модели, не вместо неё.

### R4 — Markdown-переносимость и расширенные виды (decision)

- Отдельное архитектурное решение о Dashboard-as-Markdown/YAML, миграции и совместимости.
- Timeline и Graph View получают roadmap только после R1–R3; они не компенсируют отсутствие рабочих Relations.

## 6. Правила backlog и приемки

- Каждый product ticket обязан ссылаться на сцену из §4 и иметь проверяемый user outcome.
- Каждый Relation ticket включает: создание, редактирование, обратную связь, empty/unmatched, keyboard path и реактивное обновление.
- Для P0/P1 user-flow задач 4 технических gate необходимы, но недостаточны: нужен manual scenario check в `OBStests` и screenshot evidence.
- Не смешивать «исправлен crash» и «пользователь понял flow»: это разные статусы.
- Не добавлять новый dashboard config UI до ответа: помогает ли он R1–R3 или заменяет понятный flow ещё одной настройкой?
