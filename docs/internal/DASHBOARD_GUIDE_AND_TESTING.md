## Часть I. Что такое дашборд и из чего он состоит

### 1.1 Виды (Views)
Проект Projects Plus — это набор **видов** над одним источником данных (папка / тег /
native-query). Демо содержит 5 видов:

| Вид | Тип | Что показывает |
|---|---|---|
| **Обзор** | `dashboard` | Свободный канвас с виджетами (stats, chart, database-call) |
| **Pipeline** | `board` | Канбан-доска, колонки по статусу |
| **График** | `calendar` | Календарь по датам (startDate/startTime/endTime) |
| **Клиенты** | `dashboard` | Канвас: stats + блок данных по клиентам |
| **Портфолио** | `gallery` | Карточки с обложками (cover) |

Тип `dashboard` — это и есть «дашборд-канвас»: на нём живут виджеты. Остальные типы
(board/calendar/gallery/table) — это «линзы» над данными, их же можно встроить внутрь
виджета `database-call` как вкладки.

### 1.2 Виджеты дашборд-канваса
| Виджет | Назначение | Драйвер? | Приёмник? |
|---|---|---|---|
| **stats** | Сводные показатели (count, sum, avg…) | — | ✅ (реагирует на выбор) |
| **chart** | Бар/линия/пай по полю + агрегату | ✅ (клик по бару/слайсу) | — |
| **database-call** | Встроенная база с вкладками-видами (board/calendar/gallery/table) | ✅ (клик строки таблицы) | ✅ (через связь) |

Легаси-типы (`data-table`, `summary-row`, `data-list`, `view-port`) автоматически
мигрируют в `database-call`/`stats` — отдельно их конфигурировать не нужно.

### 1.3 Меню виджета (⋯)
У каждого виджета всегда видимое «⋯»-меню с подписями:
**Настроить · Конвейер · Переименовать · Закрепить · Удалить**.
Переименование также по двойному клику на заголовке.

## Часть II. Как работать с дашбордом

### 2.1 Создать дашборд-вид
1. Открыть проект → панель видов → **+ → Дашборд**.
2. Пустой канвас показывает **zero-state**: иконка + CTA (добавить блок данных / шаблоны).

### 2.2 Добавить и настроить виджет
1. CTA «блок данных» или кнопка добавления → выбрать тип.
2. **⋯ → Настроить** открывает slide-in панель настроек (§3-анатомия: аккордеоны,
   человеческие подписи, field-пикеры с иконкой типа).
3. Для `database-call`: внутри — вкладки видов; **+** добавляет вкладку, при создании
   выбирается тип (Table/Board/Calendar/Gallery), имя по типу, переименование по dblclick.

### 2.3 Конвейер преобразования данных (transforms)
Конвейер — это цепочка шагов, применяемых к данным виджета **перед показом**.
Открывается **⋯ → Конвейер**. Доступные шаги:
**Фильтр · Группировать · Агрегировать · Вычислить · Развернуть (unpivot) · Свернуть
(pivot) · Сбросить (unset)**.

Ключевые свойства (после эпика #099 — модель Notion, без «Сохранить»):
- **Живое применение**: каждый шаг применяется мгновенно, со счётчиком `N→M` записей.
- **Правка существующего шага** (#105, фикс 2026-06-26): смена поля в «Group by field»,
  переключатель «Отключить шаг» 👁 и «+ Add condition» применяются мгновенно и **без краша**
  (раньше бросали `TypeError: Cannot assign to read only property` — мутация immer-frozen
  массива; теперь редьюсеры в `pipelineSteps.ts` иммутабельны).
- **Отключить шаг** (non-destructive): шаг с 0 записей подсвечен, можно отключить без удаления.
- **Очистить конвейер** (#075): кнопка `trash-2` в футере редактора — один клик удаляет
  ВСЕ шаги. Не разрушает данные (чистит только конфиг шагов, источник нетронут).
- **Обучающий empty-state** (#075): пустой редактор показывает пример «было→стало».
- **Фильтр-pills** в шапке вида (#103) — единственная поверхность фильтра вью (не дублируется).

### 2.4 Восстановление из пустого конвейера (#092)
Если шаги конвейера отсекли **все** записи (вход был непустой), виджет вместо «пусто»
показывает **recovery-узел**:
> 🛈 «Конвейер скрыл все записи (N шагов)»  → [Открыть конвейер] [Очистить конвейер]

Это отличает «конвейер всё скрыл» от «источник реально пуст» — у пользователя есть путь назад.

## Часть III. СВЯЗИ (relations) — как устроены и как тестировать

> Это самая важная и самая хрупкая часть. Связи реализованы через **Selection Bus** —
> per-canvas механизм выбора, связывающий виджеты на ОДНОМ канвасе.

### 3.1 Модель: мастер (драйвер) → приёмник (receiver)
- **Драйвер** публикует «выбор» (`SelectionState`), когда пользователь кликает элемент:
  - **строку таблицы** в `database-call` (пункт меню строки **«Фильтровать связанные блоки по этой строке»**, ключ `filter-canvas`);
  - **бар/слайс** в `chart`.
- **Приёмник** авто-фильтруется по этому выбору:
  - `database-call` с настроенной **связью** (`linkedSelection`) — фильтрует свои записи
    по `relationField` = значение выбора мастера;
  - `stats` — пересчитывает показатели под выбор.
- **Изоляция**: один Selection Bus на ОДИН `DashboardCanvas`. Два канваса независимы.
- **Self-skip**: драйвер не фильтрует сам себя своим же кликом.
- **Escape** очищает выбор по всему канвасу (#106, фикс 2026-06-26: обработчик переведён в
  capture-phase в `canvasSelectionStore.ts`, теперь срабатывает даже если фокус внутри
  виджета). Повторный клик по активной строке — тоже снимает выбор.

Технически (`canvasSelectionStore.ts`): при выборе мастера приёмник получает условие
`{ field: relationField, operator: "is"/"is-any-of", value: <выбор> }`, логически
AND-нутое с пользовательскими фильтрами.

> **Матч связи (#106, фикс 2026-06-26):** значение выбора мастера — это имя записи
> (`"Acme Studio"`), а Relation-поле приёмника хранит wikilink (`"[[Acme Studio]]"`). Раньше
> прямое сравнение давало «Нет совпадений». Теперь `database-call`-приёмник нормализует обе
> стороны через `relationFilterAdapter` / `canonicalLinkKey` (strip-wikilink + trim +
> **lowercase**, т.е. матч **регистронезависим**, паритет с `relationResolver`). Канонический
> контракт Selection Bus при этом **не менялся** (заморожен) — нормализация живёт на границе
> приёмника, не в `filterEvaluator`.

### 3.2 Как настроить связь в UI
1. На приёмнике (`database-call`): **⋯ → Настроить** → секция связи.
2. Селект **«Мастер-блок»** — выбрать виджет-источник на этом же канвасе
   (`linkedSelection.sourceWidgetId`).
3. Селект **«Поле связи»** — поле В ЭТОМ блоке, которое ссылается на мастера
   (`linkedSelection.relationField`, напр. `client`).
4. Пусто в «Мастер-блок» = связь снята.

Поле связи в данных хранится как **wikilink**: `client: [[Acme Studio]]`.

### 3.3 Как это уже проведено в демо (точные id)
Вид **«Обзор»**, два соседних `database-call`:
- **Мастер** `w-...648` — список **клиентов** (драйвер).
- **Приёмник** `w-...649` — **проекты клиента**, `linkedSelection.sourceWidgetId=…648`,
  `relationField="client"`.

Данные демо: 6 клиентов, 8 проектов; у каждого проекта `client: [[…]]` указывает на клиента.

### 3.4 ПОШАГОВЫЙ ТЕСТ СВЯЗЕЙ (визуально, в OBStests)

**Сценарий A — таблица-мастер драйвит проекты:**
1. Открыть демо → вид **«Обзор»**.
2. В блоке-мастере (клиенты) у строки открыть меню строки (hover → ⋯ или ПКМ) →
   **«Фильтровать связанные блоки по этой строке»** на клиенте, например **Acme Studio**.
3. **Ожидание**: блок-приёмник (проекты) показывает ТОЛЬКО проекты Acme Studio
   («Redesign — Acme Studio», «Onboarding Flow — Acme Studio»). Строка-мастер
   подсвечена как driving. _(Регресс-пункт #106: до фикса 2026-06-26 здесь было
   «Нет совпадений» из-за wikilink-mismatch.)_
4. Повторно кликнуть тот же пункт на той же строке → выбор снят, проекты показывают все.
5. Нажать **Escape** в любом месте канваса → выбор снят. _(Регресс-пункт #106: до фикса
   Escape не снимал выбор.)_

**Сценарий B — chart-мастер драйвит stats/блоки:**
1. На канвасе с chart (по статусу) кликнуть **бар** «In Progress».
2. **Ожидание**: stats и связанные блоки пересчитываются под выбранный статус;
   повторный клик / Escape снимают.

**Сценарий C — мульти-выбор (`is-any-of`):**
1. Выбрать мастер с несколькими значениями (где поддержано) → приёмник фильтрует
   оператором `is-any-of` (несколько клиентов сразу).

**Сценарий D — негатив (не должно срабатывать):**
1. Связь настроена, но активного выбора нет → приёмник показывает ВСЕ записи (не пусто).
2. Если приёмник пуст из-за linked source без выбора — это НЕ recovery-узел конвейера
   (#092 не должен ложно срабатывать); ожидается обычный empty/no-matches.

### 3.5 Как проверить связь без рендера (данные/контракт через API)
Связь опирается на корректные данные. Через REST API (без глаз) проверяемо:
- **Wikilink relation в frontmatter**: `GET /vault/<note>.md` с
  `Accept: application/vnd.olrapi.note+json` → `frontmatter.client == "[[Acme Studio]]"`.
- **Конфиг связи в data.json**: `projects[].views[].config.widgets[].config.linkedSelection`
  → `{ sourceWidgetId, relationField }` присутствует и `relationField` указывает на
  существующее поле.
- **Целостность мастера**: `sourceWidgetId` указывает на существующий виджет ТОГО ЖЕ канваса.

> Что API НЕ покажет: реальную подсветку driving-строки, фактическое сужение приёмника,
> Escape-очистку, мульти-выбор — это пиксельные пункты, нужен человек (см. §5).

## Часть V. Методология: что автоматизируемо, что — глазами

| Слой | Чем проверять |
|---|---|
| Логика бакетов/конвейера/фильтра | **Jest** (162 suites / 2287 tests, baseline 2026-06-26): `pipelineSteps`/`PipelineEditor.mutation` (#105), `relationFilterAdapter` + `canvasSelectionStore` escape (#106), `chartDataPipeline` group-mode (#107), `filterHelpers` (#108), `boardHelpers` (#109), `bucketLabelForRaw`, `pipelineRecovery`, `composeEffectiveFilter` |
| Данные / контракт frontmatter / структура проекта | **REST API** (`MANUAL_TESTING_PIPELINE.md` A1–A7 + roundtrip) |
| Рендер легенд, recovery-узла, empty-state, подсветка связей, toggle групп, локали, темы | **Глаза человека** (`UNTESTABLE_FEATURES_2026-06-26.md` — стек #105–#109, 11 пунктов; + исторический `UNTESTABLE_FEATURES_W2_2026-06-22.md`) |

**Правило**: `POST /commands/...` возвращает 2xx даже если вид упал при рендере —
зелёный API-ответ ≠ рабочий UI. Связи (§3) тестируются ТОЛЬКО визуально + данными,
их «работу как целого» API не подтверждает.

визуальные пункты структурированы по шагам — это клики по списку, а не отлов багов вслепую.
