## 3. Качество сборки

### 3.1 Что уже исправлено сегодня (см. `0ae224c`)

Ревью пушнутого диапазона нашло то, чего не нашли четыре гейта, кросс-модельная проверка и живой
прогон: `styles.css` уехал в пререлизы 55–58 без рукописной половины (7 645 байт вместо 34 964).
Механизм — `mergeCSS` читает отсутствующий файл как `""`. Восстановлено, добавлен ратчет **R0.8**,
`mergeCSS` теперь отказывается писать стиль из одних токенов, а `catch(() => process.exit(1))`
получил сообщение — до этого упавшая сборка не печатала ничего.

### 3.2 Идентичность релиза не сходится — блокер

`ci.yml` на **каждый** пуш в `main`: собирает, гоняет гейты, делает `cp manifest-beta.json
manifest.json`, публикует пререлиз с тегом `0.0.0-${{ github.run_number }}`, затем коммитит
`manifest-beta.json` обратно в `main`.

Отсюда три несовпадающих числа для одной и той же сборки:

| Где | Значение |
|---|---|
| Тег GitHub-релиза | `0.0.0-58` |
| `manifest.json` внутри артефакта | `3.5.1-beta.58` |
| `manifest.json` и `package.json` в репозитории | `3.5.1-alpha` |
| `versions.json`, последняя запись | `3.5.1-alpha` (записи `3.5.0` нет вообще) |

Для пользователя релиз называется `0.0.0-58` — это ничего не значит. Obsidian при этом покажет
`3.5.1-beta.58`. Прежде чем объявлять пре-альфу, надо решить, какое число настоящее.

### 3.3 Отсутствие 3.5.0 в `versions.json`

`src/ui/views/Dashboard/types.ts` обосновывает сохранение ключей `subBases` тем, что
«3.5.0-alpha **SHIPPED** a `SubBaseCanvas` widget». Версии `3.5.0` в `versions.json` нет —
последовательность идёт `3.4.2-alpha.1 → 3.5.1-alpha`. Либо аргумент в коде опирается на версию,
которой не было, либо `versions.json` неполон. Это надо выяснить: от ответа зависит, обязаны ли мы
дальше тащить `DataTableConfig.subBases`.

### 3.4 Вес репозитория: 12,3 МБ собранных бандлов в дереве

`.gitignore` объявляет политику — «Don't include the compiled main.js file in the repo. They should
be uploaded to GitHub releases instead» — и тут же её отменяет строкой `!releases/*/main.js`.

| Что | Объём |
|---|---|
| `releases/` — 32 файла, из них 7 бандлов `main.js` | **12,3 МБ** |
| корневой `main.js` (отслеживается, хотя правило его запрещает) | 2,78 МБ |
| `.git` целиком | 61 МБ |

Корневой `main.js` отслеживается только потому, что правило появилось позже него: `.gitignore` не
снимает файл с учёта задним числом. Ни `ci.yml`, ни `release.yml` закоммиченный бандл не читают —
оба собирают свой. Практическая цена: любые две ветки, которые собирались, дают неразрешимый
конфликт в минифицированном файле (сегодня это уже случалось), и CI-раннер работает с грязным
деревом.

**По решению пользователя это уходит в аудит Codex (#171), а не правится здесь**: смысл ограничения
в том, чтобы публикации бандла шли отдельным релизом, и менять это надо с полным разбором.

### 3.5 Хук `check-commit-branch` даёт ложные срабатывания

Хук ищет подстроку `git commit` в тексте команды и читает текущую ветку **до** выполнения. Отсюда
два наблюдённых сегодня отказа, оба ложные:

1. `grep -n "git commit" .github/workflows/ci.yml` — блокируется, потому что шаблон поиска содержит
   искомую строку. Читать workflow на `main` невозможно.
2. `git checkout -b X && git commit …` одной командой — блокируется, потому что на момент проверки
   HEAD ещё на `main`. Приходится разбивать на два вызова.

Инвариант 12 при этом правильный и должен остаться — чинить надо реализацию, а не правило.
