# Как участвовать в Projects Plus

[English](CONTRIBUTING.md)

Projects Plus — плагин Obsidian, форк [Obsidian Projects](https://github.com/marcusolsson/obsidian-projects). Это руководство о том, как собрать плагин, изменить его и проверить результат. Разработка координируется через [Клаудекс / Claudex](https://github.com/ParkPavel/claudex).

## Собрать локально

Нужен Node.js 22 — та же версия, что в CI, — и npm. Из клона репозитория:

```sh
npm ci
npm run build
```

Сборка проверяет типы TypeScript и собирает плагин через esbuild. Файлы, которые нужны в хранилище: `main.js`, `manifest.json` и `styles.css`. Для пересборки на каждое сохранение запустите `npm run dev`.

Чтобы проверить плагин в Obsidian, скопируйте эти три файла в `.obsidian/plugins/obs-projects-plus/` отдельного тестового хранилища. Создайте папку, если её нет, включите плагин в настройках сторонних плагинов и перезагружайте его после каждой сборки. Работайте на примерных заметках: проверка редактирования и удаления меняет файлы хранилища.

## Найти нужный код

Начните с [карты устройства проекта](docs/architecture.md). Плагин написан на TypeScript и Svelte, использует API Obsidian и хранилища Svelte. Точные зависимости и параметры компилятора — в [package.json](https://github.com/ParkPavel/obs-projects-plus/blob/main/package.json), [package-lock.json](https://github.com/ParkPavel/obs-projects-plus/blob/main/package-lock.json) и [tsconfig.json](https://github.com/ParkPavel/obs-projects-plus/blob/main/tsconfig.json).

Авторам сторонних видов нужен [справочник API](docs/api-RU.md). Внутренние модули — детали реализации и могут меняться между выпусками.

## Вносить изменение

Создайте ветку от `main`. Опишите задачу и поведение, которое должно получиться, и держите реализацию вместе с её документацией в одном pull request.

- Сохраняйте текст заметки при правке свойств. Используйте существующий data API и его путь через `processFrontMatter` Obsidian, а не перезапись файла целиком из компонента интерфейса.
- Пишите настройки только существующим модулем записи настроек — иначе теряются повторные попытки, обнаружение конфликта и сообщение об отказе.
- Стройте DOM безопасными для текста способами. Для поддержки отдельных окон берите документ владеющего элемента или активный документ Obsidian.
- Проверяйте данные из настроек и пользовательский ввод. Где уместно, используйте [помощники для регулярных выражений](https://github.com/ParkPavel/obs-projects-plus/blob/main/src/lib/helpers/regexSafety.ts).
- Используйте переменные темы Obsidian и [токены оформления](https://github.com/ParkPavel/obs-projects-plus/blob/main/src/ui/tokens/tokens.css). Управление должно работать с клавиатуры, а кнопкам без подписи нужны доступные имена.
- Освобождайте подписки, обработчики событий и прочие ресурсы при закрытии вида.
- Держите типы осмысленными. Неизбежные подавления объясняйте, а временный отладочный вывод убирайте до ревью.

Форматирование настроено в репозитории. `npm run format` переписывает весь `src`, поэтому просматривайте его диф и не приносите посторонних правок форматирования.

## Проверить результат

Из корня репозитория:

```sh
npm run build
npm test -- --runInBand
npm run lint
npm run svelte-check
```

Во время работы удобны точечные тесты; перед отправкой pull request прогоняйте весь набор. Тесты лежат рядом со своими модулями и в `src/__tests__`. Исправляя поведение, которое может вернуться, добавляйте покрытие. Для правки одной документации проверьте ссылки, примеры и тесты, которые сверяют изменённый справочный материал.

Изменения интерфейса нужно проверить и в Obsidian: откройте затронутый вид, выполните изменённое действие и убедитесь в результате после повторного открытия вида или перезагрузки плагина, если дело касается сохранения. Опишите в pull request хранилище, версию Obsidian и проделанные проверки — без содержимого личных заметок.

## Перевести интерфейс

Переводы интерфейса лежат в [src/lib/stores/translations](https://github.com/ParkPavel/obs-projects-plus/tree/main/src/lib/stores/translations): английский, русский, украинский и упрощённый китайский. Ключи добавляйте или правьте во всех четырёх файлах. Подписи держите короткими, а незнакомые понятия объясняйте в руководстве пользователя.

Опорный текст — английский. Русские, украинские и китайские строки для недавних функций (раскладки и размер карточек галереи, поля карточки, изменяемые рамки карточек, миниатюры в канбане, вкладка «Фильтры» в настройках) написаны сопровождающими без проверки носителями языка. Правки от тех, кто пользуется плагином на этих языках, приветствуются:

- **Сообщить о неудачной формулировке.** Откройте issue по форме [Translation](https://github.com/ParkPavel/obs-projects-plus/issues/new?template=translation.yml): язык, где в плагине встречается текст, текущий вариант и ваше предложение. Снимок экрана помогает.
- **Исправить самому.** Найдите текущий текст в файле языка — так найдётся его ключ; поменяйте значение, ключ не трогайте. Каждую подстановку вида `{{count}}` или `{{name}}` сохраняйте в точности, текст вокруг неё можно переставлять.
- **Проверить перед pull request.** `npm test -- R0_26_i18nKeyCoverage` проверяет, что каждый ключ есть во всех четырёх файлах с теми же подстановками, а `npm test -- R0_30_sentenceCase` — регистр в английском.
- Если подпись не помещается в отведённое место, это тоже проблема вёрстки: напишите об этом в issue, а не сокращайте смысл.

## Документация парная

У каждого документа есть версия на двух языках: файл с базовым именем и файл с суффиксом языка (`-RU` или `-EN`). Указатель [docs/README.md](docs/README.md), [коды ошибок](docs/ERROR_CODES.md) и две короткие страницы внутри хранилища держат оба языка в одном файле. Парность проверяет тест `src/__tests__/R0_25_documentationPairs.test.ts`: правите один язык — правьте и второй в том же коммите.

## Отправить pull request

Напишите, что было не так, что происходит теперь и как вы это проверили. Для видимых изменений приложите снимки экрана, упомяните ограничения и проверки, которые выполнить не удалось. Обновляйте руководство пользователя или справочник API, когда меняется поведение. Изменения, заметные при обновлении, записывайте в [CHANGELOG.md](CHANGELOG.md) и [CHANGELOG-RU.md](CHANGELOG-RU.md).

Не включайте учётные данные, содержимое хранилища, локальные журналы и настройки, привязанные к вашей машине. Об ошибках сообщайте через [GitHub Issues](https://github.com/ParkPavel/obs-projects-plus/issues): шаги воспроизведения, версии плагина и Obsidian, операционная система, ожидаемый и фактический результат.

## Выпустить версию

Релиз выпускается из `main`, который принимает изменения только через pull request с зелёной проверкой `build`.

1. В ветке задайте версию командой `npm version X.Y.Z --tag-version-prefix="" --no-git-tag-version`. Хук `version` копирует её в `manifest.json` и добавляет в `versions.json`; сам он версию не повышает.
2. Обновите обе истории изменений, пересоберите `npm run build` и закоммитьте `main.js` — он хранится в Git и должен совпадать с коммитом релиза. Собирайте из копии с концами строк LF: при `core.autocrlf` в Windows пробелы в шаблонах Svelte уносят `\r` в бандл, и он перестаёт совпадать с релизом, который CI собирает на Linux. Эталон — файл из релиза; при сомнении закоммитьте его.
3. Слейте pull request и запушьте тег `X.Y.Z` — саму версию, без `v` — на коммите слияния. Релизный workflow отклоняет тег, не совпадающий с `manifest.json`, собирает плагин и публикует `main.js`, `manifest.json` и `styles.css`.

Бета для [BRAT](https://github.com/TfTHacker/obsidian42-brat) — это тег `X.Y.Z-beta.N` на коммите `main`, где `X.Y.Z` выше текущей версии (после 3.7.0 — `3.7.1-beta.1`): workflow публикует её как предрелиз с бета-версией в манифесте релиза, не меняя `manifest.json` в `main`.
